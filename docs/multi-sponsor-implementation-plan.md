# Vio — Multi-Sponsor Implementation Plan

Companion to `multi-sponsor-architecture.md`. That document is the **what** (design, contracts, flows). This one is the **how and when** (phased execution).

Read alongside. The architecture doc is the single source of truth for endpoint shapes and schema; this plan references it.

**Scope status**:
- ✅ Phase 0 already complete (feature branch `feature/shoppable-ad-activations` includes `shoppable_ad_activations` table + 4 entry points + TV SDK endpoint).
- 🚧 Phases 1–9 to execute on a new branch `feature/multi-sponsor-redesign`.

---

## Principles

1. **Schema first, non-breaking**. Add columns/tables before requiring them. Enforce NOT NULL only after backfill.
2. **One concern per PR**. Don't mix schema + routes + dashboard + SDK changes in the same PR. Each phase is reviewable.
3. **Neon branch per feature**. Every structural change gets its own DB branch forked from `develop`. Merge to develop only after tests pass.
4. **Contract frozen before SDKs start**. iOS and Kotlin teams need a locked `/v1/sdk/config` response to build against.
5. **Backfill is a first-class deliverable**. Write migration scripts with `--dry-run` default, reviewed before `--yes`.
6. **Don't touch demo data**. Viaplay (app 17) and TV2 (app 18) campaigns stay intact throughout.

### Phase 2 — Data backfill

**Goal**: Populate the new columns with correct values so Phase 3 can enforce NOT NULL.

**Branch**: `feature/multi-sponsor-backfill` (stacked on Phase 1).

**Files**:
- `scripts/backfill-users-external-id.ts`
- `scripts/backfill-campaigns-primary-sponsor.ts`
- `scripts/backfill-sponsors-payment-methods.ts`
- `scripts/backfill-components-sponsor.ts`
- `scripts/backfill-polls-contests-sponsor.ts`
- `scripts/backfill-broadcasts-engagement-enabled.ts`

**Each script**:
- Default dry-run, `--yes` to execute, transactional
- Logs rows affected, rows ambiguous, rows skipped
- Idempotent (safe to re-run)

**Order**:

1. `users`: backfill `external_user_id = reachu_user_id`. For `client_app_id`, use heuristic (most common app in poll_votes for that user, or first poll_vote's app). Log ambiguous rows.
2. `campaigns`: `primary_sponsor_id = sponsor_id`. If null, skip (operator resolves manually).
3. `sponsors.payment_methods`: copy from campaigns where this sponsor is primary. If conflict (multiple campaigns with different methods), log and pick most recent.
4. `campaign_components.sponsor_id = campaigns.primary_sponsor_id` (for the campaign_id of each component).
5. `scheduled_components.sponsor_id = campaigns.primary_sponsor_id`.
6. `polls.sponsor_id, contests.sponsor_id = campaigns.primary_sponsor_id` (via broadcast → campaign).
7. `broadcasts.engagement_enabled = true` where the broadcast has at least one poll or contest, else false.

**Tests**: run each script in dry-run against Neon feature branch; verify expected row counts; fix edge cases before running with `--yes`.

**Rollout**: apply in order against Neon develop after backfill passes on feature branch.

### Phase 3 — Enforce NOT NULL + unique constraints

**Goal**: Lock in invariants now that data is consistent.

**Branch**: `feature/multi-sponsor-constraints` (stacked on Phase 2).

**Changes**:

```sql
ALTER TABLE campaigns            ALTER COLUMN primary_sponsor_id SET NOT NULL;
ALTER TABLE users                ALTER COLUMN external_user_id SET NOT NULL;
ALTER TABLE users                ALTER COLUMN client_app_id SET NOT NULL;
ALTER TABLE users                ADD CONSTRAINT users_client_app_external
                                 UNIQUE (client_app_id, external_user_id);
ALTER TABLE campaign_components  ALTER COLUMN sponsor_id SET NOT NULL;
ALTER TABLE scheduled_components ALTER COLUMN sponsor_id SET NOT NULL;
ALTER TABLE polls                ALTER COLUMN sponsor_id SET NOT NULL;
ALTER TABLE contests             ALTER COLUMN sponsor_id SET NOT NULL;
```

**Tests**: Drizzle schema compiles with non-null types. Existing routes still work (they don't yet write new columns so nothing changes at runtime).

**Risk**: if Phase 2 left any row with a null where NOT NULL is enforced, this fails. Mitigation: run validation query before each ALTER.

## Risk log

| Risk | Impact | Mitigation |
|---|---|---|
| Phase 2 backfill leaves ambiguous rows | Phase 3 NOT NULL fails | Dry-run reports; manual review of ambiguous cases; fix before `--yes` |
| iOS SDK 0.3.0 breaks Viaplay/TV2 production | User-facing breakage | Keep v1 endpoint alive in Phase 4; partners migrate on their schedule |
| Kotlin SDK contract drift from iOS | Inconsistency between platforms | Shared JSON fixtures + contract tests in both SDK repos |
| Secondary sponsor commerce key leak via /v1/sdk/config | Security | Same exposure as today; flag as known + revisit in a future phase |
| Neon branch merge conflicts when multiple features stack | Lost migrations | Keep branches rebased; merge phases sequentially, not in parallel |
| Cart intent `activationId` not wired from TV SDK on day one | Attribution gap for early TV traffic | Accept null; dashboards note "attribution available after SDK 0.3.0" |
| Commerce's product ids missing when feature DB forks stale Commerce config | Broken product hydration in tests | Include product id sync validation in seed-data script |
| Dashboard operator removes secondary sponsor with active components | 409 from backend — confused UX | Dashboard displays affected components before confirming remove |

## Resolved decisions (locked 2026-04-22)

1. **SDK endpoint versioning**: **Flip to `/v2/sdk/config`**. No parallel `/v1` window. Legacy v1 removed in Phase 8.
2. **Kotlin SDK repo**: **Separate repo** (not monorepo with iOS).
3. **Mixpanel key**: **Host-provided + Vio fallback**. Each partner puts theirs in local SDK config; if absent, SDK uses Vio's default project key.
4. **Commerce sync**: **Manual entry + webhook updates**. Operator enters the keys in the Sponsors page initially; Commerce pushes updates via a webhook to Vio (schema TBD in a separate integration doc).
5. **Reachu legacy**: **100% out**. No backfill. Reachu columns and the end-user-as-varchar pattern retired. New model: operators stay in `users` (no reachu column); end-users live in a new `end_users` table identified by `(client_app_id, external_user_id)`.
6. **`engagement_enabled` default**: **false**. Operator opts in explicitly per broadcast.

**Implication of decision 5 for Phase 2** (backfill simplified):
- `users` table: just DROP `reachu_user_id`. No migration needed.
- New `end_users` table created in Phase 1. No backfill — end-users register fresh via `ensure_user` flow on SDK init.
- `poll_votes.user_id`, `contest_participations.user_id`, `device_tokens.user_id` migrate from `VARCHAR` to `end_user_id INTEGER` FK. Historical varchar values are either deleted or left as orphan strings (recommend delete; feature DB branch already clean).

See `multi-sponsor-architecture.md` §0 and §3.2 for the full schema impact.
